# DECISIONS

One line per non-obvious choice, with the reason. Append; never rewrite history.

## Phase 0

- **D-001 — Product is Nudge; repo is `C:\Users\Pichau\Documents\Nudge.ai`.** Working name "Chaser" retired. Using **Nudge** as the wordmark and product name in all UI and copy, **nudge.ai** as the domain and repo directory — a bare "Nudge" reads better in a button, a subject line, and a sentence than "Nudge.ai" does. Say so if you want the `.ai` carried into the wordmark itself. Unrelated to the lead-follow-up app in `FollowFlow.app/followflow/`.
- **D-002 — Neon over Supabase.** Clerk owns auth, so Supabase's auth/storage/realtime are dead weight. Neon's branching gives a throwaway DB per PR, which matters because the scheduler needs backfill rehearsals against real-shaped data.
- **D-003 — Money is `amount_minor BIGINT` + ISO-4217 `currency`.** Never a float, never a decimal string in app code. No FX anywhere (§7 forbids it), so currency is display metadata, never arithmetic input. Totals across mixed currencies are rendered as separate per-currency figures, not summed.
- **D-004 — Consolidation is modelled as `messages` ↔ `message_invoices` (many-to-many).** An outbound message covers N invoices. A FK from invoice → message cannot express the 48-hour cap and consolidation at the same time; this shape can.
- **D-005 — All scheduling rules live in one pure function, `SendGuard.decide()`.** Input is a plain snapshot struct, output is a discriminated union. No DB, no network, no ambient clock. This is what makes acceptance criterion #5 provable by unit test instead of by inspection.
- **D-006 — Injectable `Clock` adapter.** `new Date()` is banned outside `lib/adapters/clock.ts`; enforced by an ESLint `no-restricted-syntax` rule. Timezone bugs are untestable otherwise.
- **D-007 — Timezone resolution order: `client.timezone` → country code mapped to a representative IANA zone → `org.default_timezone`.** The resolved zone and its provenance are persisted on every message row, so a mis-timed send is diagnosable after the fact.
- **D-008 — Holidays are national-level, best-effort, cached in `holidays_cache`.** Weekend and 08:00–17:00 are hard rules the guard enforces; holidays are a soft skip that degrades to "send anyway" when the country is unknown. Library choice pending a licence check (see `docs/PHASE-0.md` §2.4).
- **D-009 — An invoice at the final-notice step is excluded from consolidated automated messages entirely.** It routes to the manual queue on its own. Otherwise the "final notice never auto-sends" guarantee leaks out through the consolidator, which is the one way that rule could plausibly break in production.
- **D-010 — The voice profile is re-derived from the last N *sent* messages on a schedule, not mutated incrementally on each edit.** Incremental self-training on your own output drifts. Edits are stored as evidence; derivation is a separate, reviewable step, and the resulting descriptor is user-visible and user-editable.
- **D-011 — Aging colours are fills and marks, never body text on paper.** `--mint-300` measures 1.57:1 and `--amber-500` 2.02:1 against `--paper`; both fail WCAG AA for text. Added text-weight `--mint-800` and `--amber-800` carrying the same semantics. Measured numbers in `docs/PHASE-0.md` §7.2.
- **D-012 — No dark mode in v1.** The palette in §3 is a light-paper system; a dark inversion would need a second aging scale designed from scratch, and the aging scale is the brand.
- **D-013 — Invoices imported already-overdue start `paused_manual`, not `active`.** Prevents the product's first act from being a Final Notice blast at a client's twelve-month backlog. The user opts each one in.
- **D-014 — `MAIL_MODE=sandbox` is the default everywhere except production.** The transport adapter throws on any recipient outside an allowlist. A collections product that emails a real client from a dev laptop is an unrecoverable trust failure.
- **D-015 — SMTP + IMAP is the v1 mail path; Gmail API is a later upgrade.** Gmail's restricted scopes need Google verification plus an annual CASA assessment, which is calendar time engineering cannot compress and which would leave Phase 3 finished but unusable. SMTP satisfies every requirement in §2.5 with no review. Reply detection is IMAP polling on a 2–5 minute cadence; the ladder has no rule that fires faster. **The Google verification application is a Phase 1 task** so Gmail can land in Phase 5–6 as an upgrade behind the same `MailTransport` / `MailInbox` interfaces.
- **D-016 — The heads-up step is on by default for every client, including their first invoice.** I argued for on-from-the-second-invoice on volume and deliverability grounds; overruled, and it is the right call to make on product instinct rather than on my caution — the buried-in-inbox failure mode is the one this step exists to beat, and suppressing it for new clients suppresses it exactly where nobody has a payment habit yet. Consequence accepted: outbound volume roughly doubles, most of it to invoices that were never going to be late. Mitigations in place — it stays per-client editable, it is inside the 48-hour cap and the consolidation rule, and `heads_up` open/reply rates are instrumented from Phase 3 so the default is revisited with data rather than opinion.

## Phase 1

- **D-017 — PGlite when `DATABASE_URL` is unset, node-postgres when it is set.** Docker is installed on this machine but the daemon is down, and there is no Neon account yet. PGlite is real Postgres compiled to WASM, runs the byte-identical checked-in migrations, and needs no account, container or connection string — so `npm run dev` works from a clean clone. Refused in production, where the data would live in a directory that does not survive a deploy.
- **D-018 — A dev auth adapter when Clerk keys are absent.** Same reasoning: the Phase 1 gate is "genuinely usable as a manual tracker", and that should not require signing up for anything first. It provisions an *empty* organisation — never fabricated clients or invoices, which is what §0 actually forbids. Both guards are checked when a request arrives rather than at module load (D-024).
- **D-019 — No `citext`.** Emails are lowercased in the repository layer and stored in plain `text` with a unique index. Keeps one SQL dialect across PGlite and managed Postgres, and removes an extension dependency for a normalisation rule the application should own anyway.
- **D-020 — Message, thread and sequence tables land in Phase 2, not now.** They are designed in `docs/PHASE-0.md` §2.4–2.5, but a migration should arrive with the code that exercises it. Tables nobody reads drift away from what the feature actually needs by the time it is built.
- **D-021 — No Tailwind. Plain CSS with custom properties, plus CSS Modules for the rail.** §3 requires colours to be defined once as tokens with no hardcoded hex anywhere else; that rule is trivial to state and trivial to enforce against plain CSS, and `scripts/check-tokens.mjs` does enforce it across every `.css`, `.ts` and `.tsx` in the repo. It runs in `npm run check`.
- **D-022 — Rail chips are sized within their own currency, against the largest open invoice in that currency.** Sizing a ¥500,000 chip against a $5,000 one is an implicit exchange rate, and §7 puts FX out of scope. Size therefore means "large for you", not "large in dollars". Square-rooted, so one enormous invoice does not reduce everything else to a hairline.
- **D-023 — The Aging Rail is a server component with slot-based packing.** Chips go into one of 24 discrete slots per band rather than at exact percentages. That is what makes collisions honest: a chip either gets a slot near where it belongs or joins the visible "+n" overflow cluster, and nothing is ever drawn on top of anything else or silently dropped. Position is quantised to about a twenty-fourth of a band, which is finer than anyone reads a rail. The payoff is zero client JavaScript, no measurement pass, and no post-hydration reflow.
- **D-024 — Production guards run on the request path, not at module load.** `next build` runs with `NODE_ENV=production`, and building without secrets is normal — they are injected at deploy. A module-scope throw made a keyless CI build impossible while adding nothing: the check still runs before any session is issued or any query is made.
- **D-025 — Failed form submissions echo the submitted values back.** React 19 resets an uncontrolled form once its action resolves, so a mistyped email address was emptying the other seven fields. The action returns what was posted and the form re-seeds `defaultValue` from it. Found by driving the form in a browser, not by reading the code.
